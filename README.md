# AD Security Audit (ADSA)

Read-only Active Directory security assessment for **Windows** and **Linux**. Use it only where you have explicit written authorization.

The tool runs 23 audit modules aligned with common AD assessment baselines (ANSSI / CIS / Microsoft), then writes HTML, CSV, and JSON reports with a remediation plan, quick wins, coverage gaps, and optional trend comparison against a previous run.

**Version:** 2.2.0

## What this project is

ADSA is a **read-only** Active Directory auditor. It queries a domain controller over LDAP (or LDAPS) and, when available, the RSAT Active Directory PowerShell module. It does not change directory objects.

There are three ways to run it:

| Entry point | What it is |
| --- | --- |
| Desktop GUI | Cross-platform Avalonia app. Pick domain, DC, credentials, output folder, and which modules to run. |
| CLI wrapper | Self-contained .NET 8 executable that unpacks the PowerShell engine and launches it. |
| PowerShell orchestrator | `Invoke-ADSecurityAudit.ps1` plus the `Modules/` scripts. Use this when you already have `pwsh`. |

The C# GUI and CLI embed the PowerShell engine, config, and modules as resources. At runtime they extract those files and invoke PowerShell 7 (`pwsh`). On Windows, Windows PowerShell 5.1 is used if PowerShell 7 is not installed.

The GUI is built with **[Avalonia UI](https://avaloniaui.net/) 11.3.4**.

Avalonia is a cross-platform .NET UI framework (Windows, Linux, macOS). This project uses:

### Rest of the stack

| Layer | Technology |
| --- | --- |
| GUI / CLI host | C# / .NET 8 (`net8.0`) |

Solution file: `AD-Security-Audit.sln` (Visual Studio 2022 / `dotnet` CLI).

## Requirements

- Written permission to query the target domain
- Network access to a domain controller (LDAP 389 and/or LDAPS 636)
- **PowerShell 7** (`pwsh`) on the machine that runs the audit
  - Windows: Windows PowerShell 5.1 is used if `pwsh` is missing
  - Linux: install PowerShell 7 — [Microsoft install guide](https://learn.microsoft.com/en-us/powershell/scripting/install/installing-powershell-on-linux)
- A desktop session if you use the GUI
- **.NET 8 SDK** only if you build or publish from source — [download](https://dotnet.microsoft.com/download/dotnet/8.0)

Optional on Windows: RSAT Active Directory module. When it is installed, some checks use `Get-AD*` cmdlets; otherwise the engine falls back to LDAP.

## Quick start

Clone the repository:

```bash
git clone https://github.com/ClaudiuJitea/ADSA.git
cd ADSA
```

Replace `contoso.local` and `dc01.contoso.local` with your domain and a domain controller.

### Linux

Desktop app (publishes the GUI on first run if the .NET 8 SDK is installed):

```bash
chmod +x ./run-gui.sh ./run-audit.sh
./run-gui.sh
```

Command line:

```bash
./run-audit.sh -Domain "contoso.local" -Server "dc01.contoso.local"
```

If the published CLI binary is missing, `run-audit.sh` runs `Invoke-ADSecurityAudit.ps1` directly with `pwsh`.

### Windows

Desktop app: double-click `run-gui.bat` (or `powershell -File .\run-gui.ps1`).

Command line:

```bat
run-audit.bat -Domain "contoso.local" -Server "dc01.contoso.local"
```

### In the desktop app

1. Enter the domain, domain controller, and optional username/password.
2. Choose an output folder.
3. Select modules, or keep all selected.
4. Click **Run all modules** (or **Run selected**).
5. When it finishes, open `AD-Security-Audit-Summary.html` in the output folder.

The command-line run writes the same HTML, CSV, and JSON reports to the `Output` folder in this directory by default.

## Building from source

Install the [**.NET 8 SDK**](https://dotnet.microsoft.com/download/dotnet/8.0). Confirm:

```bash
dotnet --version
```

You should see `8.x`. Restore and build the solution:

```bash
dotnet restore ./AD-Security-Audit.sln
dotnet build ./AD-Security-Audit.sln -c Release
```

### Publish self-contained binaries

Published output goes under `Publish/` (this folder is gitignored). Launchers look there first.

**Linux (x64)**

```bash
dotnet publish ./GUI/ADSecurityAuditGUI.csproj -c Release -r linux-x64 --self-contained true -o ./Publish/linux-x64-gui
dotnet publish ./CLI/ADSecurityAuditCLI.csproj -c Release -r linux-x64 --self-contained true -o ./Publish/linux-x64
```

Binaries:

- `Publish/linux-x64-gui/AD-Security-Audit-GUI`
- `Publish/linux-x64/AD-Security-Audit`

**Windows (x64)**

```bat
dotnet publish .\GUI\ADSecurityAuditGUI.csproj -c Release -r win-x64 --self-contained true -p:OutputType=WinExe -o .\Publish\win-x64-gui
dotnet publish .\CLI\ADSecurityAuditCLI.csproj -c Release -r win-x64 --self-contained true -o .\Publish\win-x64
```

Binaries:

- `Publish\win-x64-gui\AD-Security-Audit-GUI.exe`
- `Publish\win-x64\AD-Security-Audit.exe`

`PublishSingleFile` and `SelfContained` are already set in both `.csproj` files, so the published file includes the .NET runtime. The machine that **runs** the audit still needs PowerShell; the published host only unwraps the engine and starts `pwsh`.

### Other runtimes

To publish for another RID (for example `win-arm64` or `linux-arm64`), change `-r` and the `-o` folder. The Linux/Windows launcher scripts expect the paths above; for other RIDs, run the published binary yourself.

### Developing the GUI

Open `AD-Security-Audit.sln` in Visual Studio 2022, JetBrains Rider, or VS Code with the C# / Avalonia extensions.

Run without publishing:

```bash
dotnet run --project ./GUI/ADSecurityAuditGUI.csproj
dotnet run --project ./CLI/ADSecurityAuditCLI.csproj -- -Domain "contoso.local" -Server "dc01.contoso.local"
```

## Running the audit

### PowerShell orchestrator (no .NET publish required)

```bash
pwsh -NoProfile -File ./Invoke-ADSecurityAudit.ps1 -Domain "contoso.local" -Server "dc01.contoso.local"
```

### Parameters

| Parameter | Description | Default |
| --- | --- | --- |
| `-Domain` | Domain FQDN or NetBIOS name | (required in practice) |
| `-Server` | Domain controller hostname or IP | same as Domain |
| `-Credential` | `PSCredential` for alternate credentials | current user, or `AD_AUDIT_USERNAME` / `AD_AUDIT_PASSWORD` |
| `-OutputPath` | Report directory | `Output` |
| `-InactiveDays` | Inactive user/computer threshold | `90` |
| `-PasswordAgeWarningDays` | krbtgt password-age warning | `180` |
| `-SkipRemoteChecks` | Skip WMI / Remote Registry checks on DCs | off |
| `-GenerateHtml` / `-GenerateCsv` / `-GenerateJson` | Report formats | `$true` |
| `-MaxObjectsPerFinding` | Affected objects listed per finding | `100` |
| `-ConfigPath` | Custom `AuditConfig.json` | `Config/AuditConfig.json` |
| `-Modules` | Comma-separated module IDs to run | all |
| `-BaselinePath` | Previous `AD-Security-Audit-Findings.json` for trend | last JSON in OutputPath |
| `-FailOnSeverity` | Exit code `2` if a failed finding at this severity or higher exists (`None`, `Critical`, `High`, `Medium`, `Low`) | `None` |

Examples:

```bash
# Subset of modules, fail CI on Critical findings
pwsh -File ./Invoke-ADSecurityAudit.ps1 -Domain "contoso.local" -Server "dc01" -Modules "TierZero,CertificateServices" -FailOnSeverity Critical

# Alternate credentials from the environment
export AD_AUDIT_USERNAME='CONTOSO\auditor'
export AD_AUDIT_PASSWORD='...'
pwsh -File ./Invoke-ADSecurityAudit.ps1 -Domain "contoso.local" -Server "dc01.contoso.local"
```

Do not commit credentials. Prefer `-Credential` interactively, or inject env vars from a secret store in CI.

## Desktop GUI

The Avalonia window is a frontend over the same PowerShell orchestrator:

- Connection: domain, DC, username, password, output folder, inactive-days threshold
- Option: skip remote WMI / Remote Registry checks
- Module cards: select all, clear, or pick a subset
- **Run all modules** / **Run selected** / **Stop audit**
- Live log of the PowerShell process

Scoring (`RiskScoring`) and reporting always run at the end, even if you deselect some audit modules.

## Configuration

Edit `Config/AuditConfig.json` to change baselines. Only these keys are used:

| Key | Purpose |
| --- | --- |
| `PreferLdaps` | Try LDAPS (636) before LDAP (389) |
| `MaxDomainAdmins` | Domain Admins count treated as excessive |
| `MinPasswordLength` / `MinPasswordHistory` | Domain password-policy baselines |
| `MaxObjectsPerFinding` | How many affected objects are listed per finding |
| `MaxTier0PasswordAgeDays` | Age at which a Tier 0 password is treated as stale |
| `MaxTrustPasswordAgeDays` | Age at which a trust account password is treated as stale |
| `SchemaChangeWindowDays` | How far back schema `whenChanged` is treated as recent |
| `MinCertificateKeySize` | Minimum published-template key size in bits |
| `ApprovedLapsReaders` / `ApprovedGmsaReaders` | Identities allowed to read LAPS / gMSA passwords |

Pass a different file with `-ConfigPath`.

## Audit modules

Coverage is 23 audit modules plus risk scoring and reporting (shown as 25 steps in the orchestrator log).

| ID | Area | What is checked |
| --- | --- | --- |
| `DomainForest` | Domain & forest | Functional levels, MachineAccountQuota, Recycle Bin, tombstone lifetime, anonymous bind |
| `DomainControllers` | Domain controllers | EOL OS, Print Spooler, DFSR, RODC password-replication policy, objects outside the Domain Controllers OU, leftover nTDSDSA metadata |
| `PrivilegedGroups` | Privileged groups | Direct and nested Tier 0 membership, inactive members, SPNs |
| `TierZero` | Tier 0 attack surface | Ownership, control ACEs, orphaned SIDs, shadow credentials, nested groups, delegation on admin accounts |
| `UsersServiceAccounts` | Users & service accounts | PasswordNeverExpires, PASSWD_NOTREQD, Kerberoast, SID history, key credential links, legacy password attributes |
| `ComputersOS` | Computers & OS | Active systems on Windows 7/8/Server 2008/2012, computer password age |
| `PasswordAuth` | Password & auth | Default domain policy, FGPP, reversible encryption, lockout |
| `Kerberos` | Kerberos | krbtgt age, AS-REP, AES on DCs, duplicate SPNs |
| `Delegation` | Kerberos delegation | Unconstrained, constrained (KCD), protocol transition, RBCD |
| `GroupPolicy` | Group Policy | GPP `cpassword`, SYSVOL secrets, GPO write ACLs and ownership |
| `ADAcl` | AD ACLs | DCSync, AdminSDHolder, Users container, OU delegation, GenericAll / WriteDacl on Tier 0 |
| `SchemaSecurity` | Schema | LAPS confidentiality, recent schema changes, default security descriptors, forest partition control |
| `Trusts` | Trusts | SID filtering, TGT delegation, RC4, stale trust passwords |
| `DNS` | DNS | AD-integrated zones with non-secure dynamic updates |
| `LdapNtlm` | LDAP & NTLM | Anonymous LDAP, signing, channel binding |
| `LapsLocalAdmin` | LAPS | Legacy Microsoft LAPS and Windows LAPS schema |
| `CertificateServices` | AD CS | ESC1–ESC5, ESC7–ESC9, ESC13, template ownership, HTTP enrollment |
| `HybridIdentity` | Hybrid identity | Entra Connect, AZUREADSSOACC Seamless SSO, AD FS farms |
| `ReplicationSites` | Replication & sites | Empty sites, NTDS settings, slow site links |
| `BuiltInPrivileges` | Built-in privileges | Pre-Windows 2000 Compatible Access, trust builders, Cert Publishers |
| `ManagedServiceAccounts` | gMSA | Inventory and overly broad password-retrieval ACLs |
| `ExchangePrivileges` | Exchange & apps | Exchange Windows Permissions, Trusted Subsystem, Organization Management |
| `AttackPaths` | Attack paths | Correlates failed checks into Tier 0 graph edges |

Risk scoring and HTML/CSV/JSON reporting always run after the selected modules.

## Reports

Each successful run writes (names may vary slightly by date) under the output folder:

- `AD-Security-Audit-Summary.html` — executive summary, findings, remediation plan (highest risk first), quick wins, coverage gaps, trend tab when a previous JSON export is present
- CSV exports of findings and attack-path edges
- `AD-Security-Audit-Findings.json` — full structured output; reuse it with `-BaselinePath` on the next run

## Tests

Engine self-tests do **not** need a domain. They parse every PowerShell file, import modules, and check helpers (LDAP escaping, Tier 0 identity detection, risk scoring, severity gate):

```bash
pwsh -File ./Tests/Invoke-AuditEngineTests.ps1
```

## Repository layout

Invoke-ADSecurityAudit.ps1     Orchestrator (module runner)

Modules/                       23 audit modules + Common, RiskScoring, Reporting

## Legal

This tool performs **authorized, read-only** directory queries. Do not run it against environments you do not own or have written permission to assess. Findings describe configuration and attack-surface conditions; they are not an exploit toolkit, and the engine does not modify the directory.
